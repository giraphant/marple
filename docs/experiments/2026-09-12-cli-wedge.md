# Marple CLI wedge investigation and resilience experiments — 2026-09-12

## Conclusion and scope

The original low-CPU wedge was **not reproduced** in three unmodified real-app
runs. TSan did **not** report the proposed SearchRanker dictionary race in the
unmodified app stress run or the focused concurrent-rebuild tests. Accordingly,
`Catalog.scheduleDeferredDerivedRebuild` and `SearchRanker` are unchanged. These
results do not prove the original process race-free or identify its root cause.

Three independently reproducible problems were repaired: unbounded metadata
waiting, ping's dependence on MainActor/cooperative execution, and organization
mutations being repeated after a lost response. The independent FTS5 per-path
quadratic deletion issue is excluded; `deletePathRows` is byte-for-byte unchanged.
No installed app or real vault was modified by these experiments.

## TSan and the dictionary hypothesis

In the inspected source, `buildSearchIndex` creates `postings` and `seenInDoc`
as local values per invocation. Seeing the function in two utility stacks is
not sufficient to demonstrate simultaneous writes to the same storage. Entries
are immutable Sendable values. The supplied sample locations remain useful
symptoms; they do not establish storage identity or the cause of no progress.

The diagnostic suite concurrently builds eight indexes from a shared immutable
10,000-entry snapshot and verifies their independent results. It also schedules
eight overlapping deferred rebuilds and verifies publication of a final,
smaller snapshot. Before production changes, both tests passed under TSan
(23.811 s), with no race report. The unmodified TSan app run `/tmp/mw-t1` completed
1,307 CLI calls, zero failures, all 10,396 entries, and all final health checks.
No sanitizer warning/report file appeared. The instrumented executable links
`libclang_rt.tsan_osx_dynamic.dylib`; a separate intentional-race positive control
produced three TSan warnings, confirming detector operation. The positive control
is never linked into Marple.

TSan uses Swift 6.3.3 from full Xcode, selected per command through `DEVELOPER_DIR`.
The default Command Line Tools compiler could not build this app's assets. One
ablation preparation attempt also hit a compiler cache alias issue (`/tmp`
versus `/private/tmp`); it was corrected before collecting the eight results.
Build/setup errors are not counted as behavioral failures. The initial TSan
bundle's copied Metal resource signature was corrected during the run; the final
combined TSan run uses a fully signed, verified bundle before launch.

## Design and implemented behavior

**Metadata:** `MetadataReader` moves `attributesOfItem` to four serial GCD workers.
Each caller waits at most 250 ms. Concurrent/repeated requests for one path join
its in-flight job; saturation skips new work, limiting blocked jobs to four per
indexer. A timeout cannot cancel a kernel stat. Reconcile reuses the collected
mtime outside the write lock and retains old rows for unavailable metadata,
while healthy paths progress. Full rebuilds retain readable content with NULL
mtime, preserving the pre-existing optional-mtime behavior.

Directory enumeration and file-content reads can still block; only the mtime
lookup is bounded here. Skipped paths are revisited on the next refresh; late
completion does not itself schedule a new pass. This matches the requested
per-path skip policy, but a new file can remain absent until another refresh.

**Socket:** accept only accepts/configures clients. Each connection gets a serial
GCD queue for blocking read/decode/write. Ping is answered there without hopping
to MainActor. Model operations still use MainActor. A silent client and a blocked
main thread therefore do not prevent another connection's ping response. Socket
timeouts remain. Both client and server suppress SIGPIPE, so an early disconnect
can yield structured recovery output instead of terminating the process.

**Mutation recovery:** the new CLI creates a UUID before each folders/tabs write
and sends a `mutate` envelope with `operation`, `requestID`, and `retryOnly`.
`--retry-request UUID` repeats the exact payload with `retryOnly: true`.
The separate wire method causes old servers to reject before applying writes;
legacy clients remain usable but do not gain idempotency.

MainActor performs lookup, the synchronous organization mutation, and response
recording without suspension. The result is recorded before socket delivery.
Matching duplicates replay the original response; changed arguments return
`request_conflict`. Errors are cached too. Cache limits are 256 records, 10
minutes, and 16 MiB of encoded payload/response data. Absent, expired, evicted,
or restarted recovery returns `request_unknown` without mutation. Inspect
`tabs list` before issuing a fresh command. This is bounded in-process recovery,
not a durable exactly-once transaction across crashes and app persistence.

The Orca reference was inspected locally in its packaged
`retry-request-flag.js` and `orchestration-mutation-recovery.js`: preserve the
mutation identity, reject malformed retry keys, and never interpret missing
recovery state as proof that the original write did not occur.

Bits are **metadata / ping / replay**. Every subset ran the same 11 named tests
(including parameterized TTL/count/byte-cap cases). Missing repairs were removed

The eleventh test guards readable-file retention in full rebuild and passes
across all variants. The synchronous metadata dependency seam, new wire protocol/client admission,
and client SIGPIPE protection are retained in every combination so identical
requests and tests compile and reach behavioral assertions. The replay bit
specifically toggles server validation/cache admission. Client early-disconnect
recovery was separately verified by a failing-before/passing-after regression. Replay-off actually executes every repeated write.
Thus 000 is a diagnostic control, not a claim to reproduce the original wedge;
the pristine app was separately exercised first, as listed above.

Concrete failure observations: the unbounded lookup waits for the 2 s cleanup
release rather than returning within its deadline; repeated stalled paths invoke
lookup four times; saturation starts eight lookups instead of two; a metadata
failure removes an existing row. MainActor blocking prevents ping from returning
before release. Without replay admission, six equal concurrent mutations create
six folders, and retry after a lost response creates a second folder.

Source hashes generated by the portable reverse-patch runner exactly match all
eight variants used in this experiment. Raw results and failure names are in
`marple-cli-resilience-results.json`; raw per-variant logs are retained in the lab.

The final combined TSan app (`/tmp/mw-t2`) completed 3,171 CLI calls
with zero failures in 226.55 s, indexed all 10,396 entries and passed
all final health checks. No `tsan*` report files or sanitizer warnings appeared.
The bundle was signed and verified before launch; it used the same large
workload with a 120 s drain period.

These runs are correctness/load checks, not controlled throughput benchmarks.
Do not infer speedups from call counts or elapsed times. The fault-injection
matrix establishes each independent repair's effect; natural pressure passing
both before and after does not establish a fix for the original wedge.

Code review caught and closed two extra regressions: requiring mtime in full
rebuild would drop readable files, and client SIGPIPE would bypass retry output.
Their tests first failed, then passed. Both normal and TSan builds passed the same relevant suite of
104 tests across 10 suites (4.934 s and 28.024 s); the CLI's 16 command mappings and five recovery
scenarios (including five early disconnect repetitions) also passed.

## Reproduce

From `apple/`, select the installed full Xcode and build/test in an isolated
copy if the checkout contains other ongoing work:

```sh
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
swift test --disable-sandbox --filter 'MetadataResilienceTests|CLIServerTests|CLIMutationReplayTests|DerivedRebuildStressTests'
swift test --scratch-path .build-tsan --sanitize thread --disable-sandbox --filter DerivedRebuildStressTests

python3 Tests/CLI/make_stress_app.py \
  --resources-from /Applications/Marple.app \
  --binary .build/debug/Marple --cli .build/debug/marple-cli \
  --output /tmp/MarpleStress.app
python3 Tests/CLI/wedge_stress.py --app /tmp/MarpleStress.app --out /tmp/mw-new \
  --seed 10000 --papers 240 --books 5 --chapters 30 \
  --interval .08 --burst-every 4 --burst-gap .7 --tabs 100 --settle 60

python3 Tests/CLI/wedge_ablation.py --out /tmp/marple-ablation-new \
  --resources-from /Applications/Marple.app
python3 Tests/CLI/retry_smoke.py .build/debug/marple-cli
```

Output directories must be new. The ablation runner copies the package, reuses
available local dependency checkouts, applies actual reverse patches, compiles
all eight subsets, and checks the exact expected failure names. With resources
provided it also assembles 100/010/001/111 apps; run each with `wedge_stress.py`
and identical arguments. `--prepare-only` verifies all patches/source hashes
without compiling. Tests require macOS socket/process access.

For a full TSan app, assemble using `.build-tsan/debug/Marple` plus the normal
CLI; `make_stress_app.py` signs and verifies the isolated bundle. Use a fresh
output and `--settle 120`. Inspect both `launch.log` and any `tsan*` reports:
a zero runner exit alone does not assert sanitizer cleanliness.

Raw investigation logs and saved binaries remain in
`/tmp/marple-wedge-20260912/`; per-process workloads remain under `/tmp/mw-*`.
Only selected structured results accompany the source; the original build log
with inherited environment is intentionally not included in repository artifacts.
