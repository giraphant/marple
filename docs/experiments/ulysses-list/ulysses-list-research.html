F01 · 原生行复用是基础，布局类型决定 cell

观察：makeViewForModelNode: 根据 displayStyle 分支，并调用 outlineView.makeViewWithIdentifier:owner:，随后配置 delegate、预览行数及元数据样式。

含义与边界：复用已有视图，避免为全部文稿创建常驻视图。静态调用不能给出实际复用命中率。

Marple 对照：EntryListTable 已使用 NSTableView.makeView 和稳定的 cell identifier；EntryHeaderCell 也复用 NSHostingView，仅替换 rootView。没有证据支持立即重写为纯 AppKit。

  • app 0x10008e620 [ULSheetTableViewController configureSheetCell:forModelNode:]

F02 · 行高按显示样式缓存，失效仍有整表后备路径

观察：heightForViewOfModelNode: 以 displayStyle 的 NSNumber 为键查询行高。缺失时创建/配置样本 view 并读取 contentSize 或 frame。invalidateCachedSheetTableRowHeight 清除相应缓存；窗口可见时通知全部行重新计算高度，不可见时调用 reloadData。

含义与边界：避免每份文稿都测量内容；不能把它描述为“永不全量刷新”。

Marple 对照：Marple 的各类行高已经是常量（header 100/124、match/toggle 24、spacer 10），比引入测量缓存更简单，应保留。

方法定位
  • app 0x10008dac0 [ULSheetTableViewController heightForViewOfModelNode:]
  • app 0x10008e418 [ULSheetTableViewController invalidateCachedSheetTableRowHeight]

F03 · 同一轮事件中的文本更新合并

观察：needsUpdateTexts 通过 isUpdatingTexts 阻止重复安排，在主 run loop 的 NSRunLoopCommonModes 安排 updateTexts；updateTexts 先复位标志。

含义与边界：多次模型通知可合并为一次行文本更新。这里没有证据表明存在固定毫秒级 debounce。

Marple 对照：scheduleReload 已有 pendingReload + main.async 合并，但合并后的工作仍可能是 buildItems + reloadData。下一步应缩小工作范围，而不是再叠一层 debounce。

F04 · 观察生命周期跟随物化的行，离窗暂停通知

观察：didAddRowView/didRemoveRowView 对 contentNodes 添加/移除观察。cell.viewDidMoveToWindow 以 window == nil 设置 nodeObserver.suspended。暂停期间事件类型在串行队列中的数组里 removeObject 后 addObject，恢复时发送记录的事件。group row 另观察 floating。

含义与边界：通知可以去重并延后投递。这证明的是离开窗口后的通知管理，不等于所有不在可见矩形内的行停止工作，也不证明后台 IO 已取消。

Marple 对照：observeModel 每轮遍历 visibleEntries 的匹配行数；这里的 visibleEntries 是筛选后的结果集，可能远大于屏幕上的行数。应区分数据集观察与实际 cell 更新。

F05 · 异步文稿加载有身份校验

观察：setSheetHandleNode: 重新绑定观察对象，已有 sheet 时直接使用，否则安排加载。loadSheetHandle 包含向全局队列派发的调用；sheetHandleFinishedLoading: 比较返回 sheet 的 handle 与当前 handle，不匹配就不更新。

含义与边界：复用行或快速切换后，旧请求不能覆盖新文稿。scheduleSheetLoadingForHandle: 使用 common modes 安排加载；加载指示的 afterDelay 参数为 0，不能称为已验证的延迟 spinner 优化。

Marple 对照：AppModel 搜索已有取消检查；Catalog 匹配加载也有取消与当前 query 校验。应保留这些守卫，未来如增加 cell 级异步预览，再增加该 cell 的身份/版本校验。

F06 · 预览长度有限，元数据缓存带新鲜度检查

观察：cell.maximumPreviewTextLength 返回 previewLineCount × 50。observer 的预览格式化调用传入最大长度。ULSheetHandle 的 contentPrefix 在 isIndexUpToDateForSheet 为真时返回 cachedContentPrefix，否则 loadSheetForReading 后重新提取。

含义与边界：存在有上限的显示预览和缓存快路径，但 stale/cold 路径仍可能读取正文；不能断言列表永远不加载全文。该元数据 getter 不是已证明的 cell 首帧调用链。

Marple 对照：普通 EntryRow 直接使用已索引的 entry.preview；firstParagraph 的输出上限为 800 字符。普通预览已有边界，搜索摘要的全文扫描是另一条路径。

F07 · 搜索匹配折叠限制展示节点，不等于限制搜索计算

观察：ULSheetHandleNode.setSearchResult: 在匹配子节点数 >= 6 且未展开时，保留完整集合，展示前 3 个节点加 placeholder；少于 6 或曾展开则展示完整集合。expandContentNodes 以完整集合替换并发送 contentNodes KVO。

含义与边界：限制可见结构规模，但之前仍枚举并构建匹配节点，不能声称只计算前三条。阈值 6、可见前缀 3 是本版本的实现细节。

Marple 对照：已采用前 3 条 + 展开按钮，且从第 4 条开始折叠。无需为性能复制 Ulysses 的阈值 6；更值得让展开/收起只改变当前文稿对应的行。

F08 · 局部匹配变化只重配受影响的边界行

观察：_updateViewsForSheetNode:oldMatches:newMatches: 更新文稿行的 separator；比较旧、新末尾匹配节点，仅在不同且非空时分别 reloadCellsForModelNode。

含义与边界：这是具体的局部刷新路径，不能由此推出所有结构更新都没有全量 fallback。

Marple 对照：目前 RowItem 携带完整 Entry，items != newItems 会走 reloadData。可以把稳定行身份与展示 payload 分开，对内容变化重配已有 cell，对小规模结构变化插入/删除/移动。

F09 · 搜索索引区分新增、替换与失效结果

观察：notifyQuery:didFindNewResults:replacedResults:invalidatedResults: 的关联 block 分别调用 delegate 的 didFindResults、didReplaceResult:withNewResult:、didInvalidateResults。performNotification: 尾调用 dispatch_async。

含义与边界：结果协议表达增量语义。这里只确认通知通道，没有测出合并频率、队列吞吐或并发上限。

Marple 对照：Catalog.computeSearchMatches 先清空旧字典，串行遍历命中文稿，最后整体发布。可评估按查询版本保留/分批发布摘要，但要先解决 UI 局部刷新，避免每个批次再触发整表刷新。

F10 · 单容器滚动位置以持久对象为键保存

观察：preserveInterfaceStateForCurrentContainer 仅在单容器且有 persistentObject 时，将 clipView.bounds.origin.y 写入 preservedScrollPosition。restore 读取该值，经 restoreLastScrollState: 调用 outlineView.scrollPoint:。

含义与边界：容器切换可以恢复位置。这条路径保存的是 y 坐标，不能称为已验证的稳定行身份锚点。

Marple 对照：当前 reload 路径保存 SelectionKey 并恢复选中项，但没有捕获 top row identity + offset。结构增量更新时应验证滚动稳定；按身份恢复顶部锚点是 Marple 的设计建议，不是照抄上述 Ulysses 代码。

F11 · 索引队列限制并发，暂停先缓存尚未提交的任务

观察：sharedIndexingQueue 的 provider 创建 NSOperationQueue，设置 maxConcurrentOperationCount；在处理器数至少为 2 的机器上，参数为 max(processorCount - 2, 1)，QoS 为 0x09（Background）。addOperation 在 suspendedOperations 非空时把新任务放入数组；resume 再逐个提交到共享队列并清空数组。

含义与边界：这是索引队列的并发限制，不是列表预览加载队列的并发上限。suspend 没有在已核对路径中取消或中断已提交的 operation。provider 的全局 block 位于 0x796208，invoke 字段解码指向 0x233444，已核对关联，非仅按 next-IMP 猜测。

Marple 对照：本轮每个搜索查询串行等待一篇正文的后台解析，避免对全部命中同时创建任务。旧查询取消后，已经开始的单篇纯计算仍会结束，但结果丢弃且不继续下一篇；若快速多次切换查询仍有 CPU 压力，再考虑细粒度取消或共享限流。

方法定位
  • core 0x23342c [ULSearchIndexOperationQueue sharedIndexingQueue]
  • core 0x2334c8 [ULSearchIndexOperationQueue addOperation:]
  • core 0x233588 [ULSearchIndexOperationQueue suspend]
  • core 0x233608 [ULSearchIndexOperationQueue resume]

F12 · 字符串索引缓存保留最近记录，并响应内存压力

观察：_unprotectedSetStringIndex:forSheetHandle: 将索引写入 _cachedStringIndexes，并把 handle 写入 _recentIndexes[nextPurgableIndex % 10] 后递增计数；缓存数量达到非零 _entryLimit 时触发 flush。flush 枚举 _recentIndexes 的 value，只把仍有缓存的 handle/index 对复制到新的强引用 map。didReceiveMemoryWarning 的 write block 将 _entryLimit 设为当时缓存数量的一半（向下取整），再 flush。

含义与边界：可证明的策略是十个最近记录槽位及压力后收缩。它不是已证明的严格 LRU，也不是按字节精确计费的缓存。没有推断“整个应用永远只缓存十份文稿”；这是一个字符串索引缓存的清理路径。

Marple 对照：搜索摘要目前没有跨查询缓存，本轮不增加。若后续测量支持添加缓存，应把版本失效与成本/内存压力处理一起设计，避免只增加一个无限增长的字典。

方法定位

  • core 0x23cdb4 [ULSheetIndex _unprotectedFlushStringIndexCache]
  • core 0x23cc94 [ULSheetIndex didReceiveMemoryWarning]

实施顺序与当前进度

P1 · 搜索摘要计算移出 MainActor

本轮最小修复已完成；单篇后台计算、串行等待、旧结果守卫。

原因：Catalog 标记 @MainActor，computeSearchMatches 的 Task 继承隔离；await entryText 返回后，同步的正文解析与逐行匹配仍占用主 actor。文件读取是否阻塞其他 executor 需另测，不能仅凭 async 签名判断。

最小改动：对已读取的字符串快照，在后台执行 Frontmatter.split + bodyLineMatches；发布仍回主 actor，保留 query/取消守卫。先用串行后台工作避免大量文稿同时驻留；不要直接创建无上限 TaskGroup。

验收：真实窗口记录主线程耗时和输入响应；覆盖 10 KB/1 MB 长文、多个搜索命中、快速改 query、清空搜索和离开页面。断言旧查询从不发布。

P1 · 区分内容刷新与结构变化

本轮最小修复已完成；采用原生局部行刷新，未引入差分框架。

原因：当前单条 Entry payload 变化也可使 itemsChanged 为真，触发整表 reloadData；每次 reload 都重建投影。

最小改动：为 header/match/toggle/spacer 定义稳定身份（spacer 归属相邻文稿），分离 payload。结构不变时更新模型并只重配变动的已物化 cell；高度样式变化时精确失效行高。保留搜索模式切换等需要换 row class 的 fallback。

验收：计数 buildItems、reloadData、cell 创建/配置、rootView 替换。单条同位置标题/评级/预览更新必须无整表 reload，保持多选与滚动，屏幕外行出现时使用新内容。

P2 · 搜索展开及小规模结构变化使用增量行更新

继续调研，尚未实施。

原因：现在展开单篇匹配仍会重投影整个结果集并 reloadData。

最小改动：在稳定身份的基础上做小差分并保留 fallback；同步恢复 SelectionKey，必要时保存顶部行身份与行内偏移。阈值通过测量确定，不直接移植侧边栏阈值。

验收：覆盖首/中/末文稿展开收起、排序移动、删除被选中项、match ordinal 变化、连续键盘导航。记录 500/5,000/15,000 条结果的 p50/p95 主线程耗时。

P2 · 摘要缓存与分批发布按测量结果决定

继续调研，尚未实施。

原因：目前对命中集合逐文稿读取并全量发布；潜在首批结果延迟存在，但缓存收益尚未量化。

最小改动：先测 IO、解析、发布各阶段。确有重复工作再使用文稿身份 + 正文版本 + query 作为缓存键，并设置成本上限与失效规则。批次发布应与 UI 增量更新配套。

验收：编辑后不能展示旧摘要，重复 query 应可统计命中率，冷/热缓存分别测量；持续滚动与多轮搜索后检查驻留内存。
